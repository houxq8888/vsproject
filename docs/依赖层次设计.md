# vsproject 依赖层次设计

## 依赖层次原则

1. **单向依赖**：低层模块不能依赖高层模块
2. **接口隔离**：通过接口层隔离具体实现
3. **依赖倒置**：高层模块不依赖低层模块，都依赖抽象
4. **循环禁止**：严禁任何形式的循环依赖

## 依赖规则

### 基础服务层规则
1. **基础服务层（第0层和第1层）可以被所有上层直接依赖**
   - 第0层提供最基础的功能（Common, Config）
   - 第1层提供原子服务（Log, Save, Frame等）
   - 第0层和第1层作为基础服务层，被所有层直接依赖是合理的

### 严格分层依赖规则
2. **第2层及以上需要遵守严格的分层依赖**
   - 第2层依赖第1层和第0层
   - 第3层依赖第2层、第1层和第0层
   - 第4层依赖第3层、第2层、第1层和第0层
   - 第5层只依赖第4层和第3.5层，不直接依赖第3层、第2层、第1层、第0层
   - 第6层依赖第5层、第4层、第3层、第2层、第1层和第0层
   - 第7层依赖第6层、第5层、第4层、第3层、第2层、第1层和第0层

### 跨层依赖限制
3. **禁止跳层依赖**
   - 第2层及以上不能跳过相邻层直接依赖更下层的模块（除了第0层和第1层）
   - 例如：第4层不能跳过第3层直接依赖第2层的模块
   - 例如：第5层不能跳过第4层直接依赖第3层的模块

### 循环依赖禁止
4. **禁止循环依赖**
   - 任何情况下都不能形成循环依赖
   - 低层模块不能依赖高层模块
   - 同层模块之间可以相互依赖，但应尽量减少

### 接口依赖规则
5. **接口依赖**
   - 第5层（UI应用模块层）应通过3.5层（UI服务接口层）访问第1层和第0层的服务
   - 第4层（接口层）应通过第3层（模块层）访问底层功能
   - 接口层主要用于隔离具体实现，符合依赖倒置原则

### 第5层特殊规则
6. **第5层特殊规则**
   - 第5层（UI应用模块层）负责UI交互，不涉及业务逻辑
   - 第5层绝对不能直接依赖第3层、第2层、第1层、第0层
   - 第5层只通过第4层（接口层）和第3.5层（UI服务接口层）访问底层功能
   - 第4层作为桥梁，确保第3层的修改不会影响第5层（不需要重新编译）

## 层次说明

### 第0层 基础设施层
提供最基础的工具类和配置管理，不依赖任何其他业务模块：
- HGCommon：基础工具类、数据结构
- HGConfig：配置管理

### 第1层 原子服务层
提供系统级的基础服务，依赖基础设施层：
- HGLogService：日志服务
- HGAuthorityService：权限服务
- HGInteractiveService：交互服务
- HGImageAlgorithmService：图像算法服务
- HGDataPostProcessService：数据后处理服务
- HGSaveService：数据存储服务
- HGFrameService：框架服务
- HGCommunicateService：通信服务
- HGErrorService：错误处理服务
- HGOTAService：OTA升级服务
- HGSecurityService：安全服务
- HGSvcCommonProtocol：通用协议服务

### 第2层 硬件抽象层
提供硬件相关的抽象接口，依赖基础设施层和原子服务层：
- HGRobot：机器人控制
- HGSensor：传感器
- HGLowerPC：下层PC通信

### 第3层 模块层
实现核心业务逻辑，依赖下层服务：
- HGCupDetModule：杯子检测模块
- HGDashboardModule：仪表板模块
- HGOnlinePlatformModule：在线平台模块
- HGV6Module：V6相关模块
- CoreLogModule：日志模块
- HGCoreDetectDimentionVux：尺寸检测模块

### 第3.5层 服务接口层 (ServiceInterfaces)
为上层（第2、3、4、5、6、7层）提供对底层服务的抽象接口，消除跨层依赖：
- IUIConfigService：配置服务接口
- IUISaveService：存储服务接口
- IUIServiceManager：服务管理接口
- IUICommonService：通用服务接口
- ICoreLogService：日志服务接口
- UIConfigServiceAdapter：配置服务适配器
- UISaveServiceAdapter：存储服务适配器
- UIServiceManagerAdapter：服务管理适配器
- UICommonServiceAdapter：通用服务适配器
- CoreLogServiceAdapter：日志服务适配器
- UIDependencyContainer：依赖注入容器
- UIServiceFactory：服务工厂

这一层的设计遵循依赖倒置原则，上层模块依赖第3.5层的抽象接口，而不是直接依赖第0层和第1层的具体实现。

### 第4层 接口层
提供模块间的接口定义，隔离具体实现：
- CameraControlInterface：相机控制接口
- CameraRecognizeInterface：相机识别接口
- HGCupDetInterface：杯子检测接口
- HGOnlinePlatformInterface：在线平台接口
- HGV6Interface：V6接口
- LogInterface：日志接口
- PackFuncInterface：打包功能接口
- HGIfDetectDimentionVux：尺寸检测接口

### 第5层 UI应用模块层

- HGAnalysisRecordModule：分析记录模块
- HGBaseAppModule：基础应用模块
- HGCameraRecognizeModule：相机识别模块
- HGChannelModule：通道模块

## 特殊处理

### 应用层分类
第6层应用层分为两类：
- **App前缀**：带UI的图形界面应用程序
- **Cmd前缀**：不带UI的控制台/命令行程序

### DetectDimentionVux模块
DetectDimentionVux相关模块分布在三层中：
- **第1层**：SvcCommonProtocol - 通用协议服务
- **第3层**：CoreDetectDimentionVux - 尺寸检测核心模块
- **第4层**：IfDetectDimentionVux - 尺寸检测接口
- **第6层**：CmdDetectDimentionVux - 尺寸检测控制台程序

这种分层设计符合依赖倒置原则，高层模块通过接口层依赖低层模块。

### 重复模块处理
注意：某些模块名称在不同层中重复出现，如：
- HGLogModule同时出现在第3层和第5层

这些重复可能是由于模块的不同职责或不同实现导致的，需要在实际开发中明确区分。

### 接口层位置
接口层位于第4层，介于模块层和UI应用模块层之间，用于隔离业务逻辑和UI实现，符合依赖倒置原则。

## 依赖注入容器设计

### 容器结构

```cpp
class ServiceContainer {
public:
    // 注册服务
    template<typename Interface, typename Implementation>
    void registerService();
    
    // 获取服务
    template<typename Interface>
    std::shared_ptr<Interface> getService();
    
    // 初始化所有服务
    void initialize();
    
    // 销毁所有服务
    void shutdown();
    
private:
    std::map<std::string, std::function<void*()>> m_services;
    std::vector<std::string> m_initializationOrder;
};
```

### 服务生命周期管理

1. **单例服务**：系统全局唯一的服务实例
2. **瞬态服务**：每次请求都创建新实例
3. **作用域服务**：在特定作用域内保持单例

## 实施步骤

1. **第一阶段**：建立基础服务层
   - 明确第0层和第1层为基础服务层
   - 第0层提供最基础的功能（Common, Config）
   - 第1层提供原子服务（Log, Save, Frame等）
   - 确认所有上层模块都可以直接依赖第0层和第1层

2. **第二阶段**：解决第5层跨层依赖
   - 创建第3.5层UI服务接口层
   - 实现IUIConfigService、IUISaveService、IUIServiceManager、IUICommonService接口
   - 实现对应的适配器类（UIConfigServiceAdapter、UISaveServiceAdapter等）
   - 创建UIDependencyContainer依赖注入容器
   - 重构第5层UI模块，将直接依赖第1层改为依赖第3.5层接口

3. **第三阶段**：解决第4层跨层依赖
   - 分析第4层模块的依赖关系
   - 确保第4层通过第3层访问底层功能
   - 更新第4层模块的依赖关系

4. **第四阶段**：建立依赖层次
   - 按照新的依赖规则重新组织模块
   - 更新CMakeLists.txt文件
   - 添加依赖检查规则

5. **第五阶段**：工具和检查
   - 完善依赖分析工具
   - 添加CMake依赖检查
   - 建立持续集成检查

## CMake依赖检查规则

```cmake
# 检查循环依赖的CMake函数
function(check_circular_dependencies target)
    # 获取目标的所有依赖
    get_target_property(depends ${target} LINK_LIBRARIES)
    
    # 检查是否存在循环依赖
    foreach(dep ${depends})
        if(dep STREQUAL ${target})
            message(FATAL_ERROR "Circular dependency detected for ${target}")
        endif()
    endforeach()
endfunction()

# 检查跨层依赖的CMake函数
function(check_layer_dependencies target layer)
    # 获取目标的所有依赖
    get_target_property(depends ${target} LINK_LIBRARIES)
    
    # 检查是否存在跨层依赖
    foreach(dep ${depends})
        get_target_property(dep_layer ${dep} LAYER)
        if(dep_layer AND dep_layer LESS ${layer})
            message(WARNING "Cross-layer dependency detected: ${target} (layer ${layer}) -> ${dep} (layer ${dep_layer})")
        endif()
    endforeach()
endfunction()
```

## 最佳实践

1. **模块设计**：
   - 每个模块只负责单一职责
   - 模块间通过接口通信
   - 避免直接依赖具体实现

2. **依赖管理**：
   - 使用依赖注入容器管理服务
   - 明确标记模块的层次
   - 定期检查依赖关系

3. **代码组织**：
   - 按层次组织目录结构
   - 使用命名空间区分层次
   - 保持接口稳定

4. **开发流程**：
   - 在CI/CD中集成依赖检查
   - 定期审查依赖关系
   - 及时重构不合理依赖

通过以上设计，我们可以建立一个清晰、可维护、可扩展的模块依赖体系，避免循环依赖和过度耦合的问题。
